# sglang-scheduler

一个用 Go 实现的轻量级内存调度原型，用来演示“任务进入全局队列，再按节点负载调度到不同节点执行”的基本思路。

## 1. 实现思想

整个调度流程可以概括为 4 个阶段：

1. **任务产生**  
   `main.go` 中持续生成任务，并调用 `Push(...)` 提交任务。

2. **进入全局队列**  
   `node_selector.go` 会把任务包装成 `TaskNode`，再放入 `global_queue.go` 中维护的全局 FIFO 队列。

3. **选择节点并调度**  
   `ScheduleFromGlobalQueue()` 会读取当前节点状态，按节点上已有任务数排序，优先把任务分配给当前负载最低的节点。

4. **节点消费任务**  
   `node_collector.go` 中的 mock 消费协程会周期性从每个节点移除部分任务，并打印消费日志。

### 当前调度策略

当前实现采用的是一种非常直接的 **最小负载优先（least-loaded first）** 思路：

- 维护一个全局任务队列；
- 获取所有节点当前任务数；
- 选出任务最少的节点；
- 将该节点补到 `threshold` 上限为止；
- 后续通过定时调度协程持续从全局队列取任务继续分配。

换句话说，当前系统是：

- **全局队列负责缓冲任务**；
- **节点任务数负责表达负载**；
- **定时调度器负责把积压任务搬运到负载最轻的节点**。

## 2. 架构流程

```text
main.go
  ├─ 生成任务
  ├─ 调用 Push(...)
  │
  ▼
node_selector.go
  ├─ 把 string 任务转换成 TaskNode
  ├─ 写入全局队列
  └─ 触发一次调度
  │
  ▼
global_queue.go
  ├─ 维护全局 FIFO 链表队列
  ├─ 批量出队任务
  └─ 按最小负载节点进行分发
  │
  ▼
node_collector.go
  ├─ 维护 mock 节点信息
  └─ 周期性消费节点任务
```

## 3. 每个模块的功能

### `main.go`

程序入口，负责：

- 创建 `context.Context`；
- 启动全局队列调度协程 `StarScheduleFromGlobalQueue(...)`；
- 启动 mock 任务消费协程 `StartMockTaskConsume(...)`；
- 持续生成任务并推送到调度入口；
- 使用 `select {}` 阻塞主线程，保持程序常驻运行。

### `node_selector.go`

调度入口模块，负责：

- 对外提供 `Push(tasks ...string)`；
- 把原始字符串任务转换为 `TaskNode`；
- 调用 `BatchPushToGlobalQueue(...)` 把任务批量写入全局队列；
- 立即触发一次 `ScheduleFromGlobalQueue()`，尽量减少排队等待时间。

这里的作用更接近“**任务接入层**”。

### `global_queue.go`

全局队列与调度核心，负责：

- 定义任务链表节点 `TaskNode`；
- 维护全局队列头尾指针与长度；
- 提供批量入队 `BatchPushToGlobalQueue(...)`；
- 提供批量出队 `BatchPopFromGlobalQueue(...)`；
- 在 `ScheduleFromGlobalQueue()` 中根据节点负载执行调度；
- 在 `StarScheduleFromGlobalQueue(...)` 中按固定周期触发调度。

这是整个仓库最核心的模块。

### `node_collector.go`

节点状态与 mock 执行模块，负责：

- 定义节点结构 `PrefillNode`；
- 初始化 3 个模拟节点：`node-a`、`node-b`、`node-c`；
- 对外提供 `GetNodesStatus()` 返回所有节点；
- 周期性随机消费节点中的任务；
- 通过日志打印任务被消费的过程。

这里的“collector”更像是一个 **模拟节点执行器 / 节点状态提供者**。

## 4. 优点

### 4.1 全局队列解耦了生产与消费

任务先进入全局队列，生产速度和节点消费速度不必完全同步，这种方式天然具备一定的削峰缓冲能力。

### 4.2 调度策略直观

按当前节点任务数选择最空闲节点，逻辑简单，容易调试，也方便后续替换为更复杂的策略。

### 4.3 支持批量操作

全局队列支持批量入队和批量出队，比单个任务逐一处理更适合后续扩展。

### 4.4 具备基础并发模型

通过 goroutine + ticker，已经搭出“提交任务 / 定时调度 / 节点消费”三段式异步模型。

---

## 5. 缺点

### 5.1 负载指标比较单一

当前只按 `len(node.tasks)` 判断负载，没有考虑：

- 节点算力差异；
- 任务权重差异；
- 执行耗时差异；
- CPU / GPU / 内存等真实资源指标。

### 5.2 并发安全仍可继续增强

虽然全局队列已经有互斥锁保护，但节点上的 `tasks` 切片目前仍是共享可变状态。对于更真实的并发场景，还需要更严格的同步设计。

### 5.3 缺少生产级调度能力

当前还没有这些能力：

- 任务优先级；
- 重试机制；
- 超时控制；
- 失败回滚；
- ACK / 完成确认；
- 节点健康检查；
- 指标监控与可观测性。

## 6. 运行方式

在仓库根目录执行：

```bash
go run .
```

如果你想执行测试：

```bash
go test ./...
```

运行后你会看到类似行为：

- 主协程不断生成任务；
- 任务进入全局队列；
- 调度器周期性将任务分配到节点；
- mock 消费器打印节点消费任务的日志。

---

## 7. 后续可以怎么演进

如果要把这个原型继续往前推进，比较自然的方向有：

1. **把节点列表改成动态注册**，而不是写死 3 个节点；
2. **把调度策略改成可插拔**，例如轮询、最小负载、加权最小负载；
3. **引入持久化队列**，比如 Redis / Kafka / 数据库；
4. **增加任务状态机**，支持 pending / running / success / failed；
5. **增加监控与日志**，统计队列长度、调度次数、节点负载等指标；
6. **补充单元测试和压力测试**，验证高并发下的正确性。

---

## 8. 总结

这个仓库实现了一个非常清晰的最小可运行调度原型：

- 有全局队列；
- 有节点状态；
- 有调度逻辑；
- 有模拟消费；
- 有基础并发模型。
